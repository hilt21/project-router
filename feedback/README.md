# 反馈闭环

仅记录真实偏差、明确用户纠正或已验证且值得复用的经验。普通成功任务可以只保留简短回执。记录失败与阻塞，成功样本若采样则注明口径。

分类：routing（选错流程）、quality（产物问题）、environment（工具环境）、conflict（规则冲突）、preference（用户偏好）、unknown（根因未明）。

先保留观察、预期、可复现输入、路由 SHA 和脱敏证据，再判断该修改属于项目规则还是跨项目候选。用户明确偏好可以直接形成项目约束；一次偶发失败先验证原因。

默认在对话中草拟反馈。当前请求或项目长期指令明确授权后，才向 hilt21/project-router 创建 Issue，并回读结果。可用的长期授权表述为：“允许将本项目的脱敏路由反馈写入 hilt21/project-router 的 Issues；不得上传完整对话、凭据和业务私密内容。”

本地 `feedback-draft` 只输出正文，不联网、不自动发帖。结构检查和凭据模式检测只能辅助脱敏，最终需审阅白名单字段和引用内容。

改进 PR 附复现、最小修改、反例、旧版与候选版结果、影响范围和回滚方式。模型自评分不构成通过证据。语法检查通过不代表 Work 执行正确。

## 反馈意图检查与去重

每条新的用户消息开始时，结合当前任务及刚完成的产物进行一次语义检查；实际执行中发现新偏差时再检查。以下情况进入反馈判定，无须用户特意说“请反馈到仓库”：

- **明确纠错**：用户指出上一输出或实际执行不符合预期，并给出修正要求。
- **长期约束**：用户明确要求项目以后持续遵守的规则、平台边界或偏好。只保留在相关项目或平台。
- **可观察故障**：路由误选、能力误判、工具失败或规则冲突等有可复核观察的偏差。原因不明时记录 unknown。
- **已验证经验**：有具体例子与证据支持，并可节省未来重复纠错的工作方法。

以下情况通常只完成当轮任务，不产生持久反馈：讨论“反馈”这个话题、粘贴或引用别人的要求、对当前一篇文案的临时改写、未核实的推测、无新增经验的常规成功。无法判明临时还是长期时，先不扩大作用域，可在有实质影响时简短确认。

确认命中后，按顺序处理：

1. 从当前已固定的源 SHA 加载 `capture-router-feedback` 及本文件。记录项目 ID、平台或阶段、源 SHA、观察、预期和脱敏证据；缺失字段标记 unknown，不能补造。
2. 在同一仓库检查已有 Issue，按项目、问题机制、适用范围和证据判断是否重复。重复时关联已有 Issue，并说明是否仍存在未解决问题；不再为同一问题创建第二条 Issue。无法检索时写明无法去重，避免盲目重复写入。
3. 识别当前请求或项目长期指令是否明确授权将脱敏反馈写到公开仓库。无授权时止于草稿；有授权且工具可用时创建 Issue 并回读 URL。提交外部数据的授权与修改代码、合并 PR、发布版本的授权分别判断。
4. 回答用户时简要交代本条反馈的结果状态：`drafted`（仅草稿）、`linked-existing`（关联旧 Issue）、`filed`（新 Issue 已回读）、`blocked`（缺权限、工具或有效证据）；附 URL 或下一步。仅当存在实质反馈时展示状态。Issue 创建完成不表示规则已修改或 stable 已发布。

本检查点由宿主 Agent 执行，属于可验证的指令行为，当前没有可靠的自动事件钩子。ChatGPT Memory 可能独立记录偏好，平台顺序不可由本仓库控制；Memory 的提示既不证明反馈 Skill 已加载，也不证明 Issue、PR 或发布完成。
